# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Internal compliance dashboard for triaging data broker removal responses at scale, built for PureWL's compliance workflow. Next.js 16 (App Router) app with SQLite/Prisma, Gmail SMTP for outbound email, a "legal workbook" module for jurisdiction-specific legal clause reference data, and a "case tracker" module for escalating broker non-response cases through a jurisdiction-aware enforcement/complaint pipeline.

## Commands

```bash
npm run dev              # dev server (http://localhost:3000)
npm run build             # production build
npm run lint               # next lint
npm test                    # jest (lib/*.test.ts — jurisdiction mapping + case business rules)

npm run db:push            # push prisma/schema.prisma to the SQLite DB
npm run db:generate        # regenerate Prisma client after schema changes
npm run db:studio          # Prisma Studio GUI
npm run db:seed            # seed 60 mock broker responses (scripts/seed.ts)
npm run db:seed:legal      # seed legal workbook mock data (scripts/seed-legal.ts)
```

## Environment

Required in `.env` (see `.env.example`): `DATABASE_URL`, `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASS`/`SMTP_FROM`, `AUTH_PASSWORD`. Note `proxy.ts` also reads `AUTH_SECRET` (used as the session cookie value compared against on every request) — this is separate from `AUTH_PASSWORD` (the login form password checked once in `app/api/auth/route.ts`). Both must be set for auth to work.

## Architecture

**Three feature areas share one app:** the broker-response triage dashboard (`/responses`), the legal workbook (`/legal-workbook`, a reference library of data-protection law clauses per jurisdiction used by legal counsel to back replies with citations), and the case tracker (`/case-tracker`, escalates broker non-response cases through a jurisdiction/authority confirmation flow). Root `/` is a Home Overview that aggregates all three (counts, activity, cases, regimes) but is otherwise read/navigate-only. Each area is a separate client-state tree — `components/dashboard.tsx`, `components/legal-workbook/legal-workbook.tsx`, `components/case-tracker/case-tracker.tsx` — sharing only layout/auth/db.

**Case jurisdiction is always derived from the user's location, never the broker's.** `lib/jurisdiction-map.ts` is the single-file, isolated mapping from `userCountry`/`userState` to regime/deadline/filing authority/complaint URL/max fine — it has no `brokerCountry` parameter, so it's structurally impossible to derive from the broker's location. `lib/case-tracker.ts` wraps it (`deriveCaseFields`) and owns stage-transition rules (`canTransitionStage`: sequential/forward-only via `getNextStage`, plus `complaint_eligible` requires jurisdiction confirmed and `complaint_filed` requires authority confirmed *and* an approved, unedited draft reply — see `assertDraftApprovedForFiling` below) and confirmation immutability (`assertConfirmable` — a confirmed timestamp can never be re-set). The `POST /api/cases` Zod schema (`lib/case-validation.ts`) is `.strict()` and only accepts intake fields, so a client can't set `applicableRegime` etc. directly even if it wanted to. Every stage advance and confirmation is logged to `CaseActionLog` (`caseId`-scoped, mirrors `ActionLog`'s role for `BrokerResponse` — see below), rendered as the case's History timeline in `case-detail.tsx`.

**Case closure and case status are two more axes independent of enforcement stage.** Evidence completeness (five items — request, identity, systems, reply, retention exception) gates closure: each item confirms individually via `assertConfirmable` (same immutability pattern as jurisdiction/authority above), and `assertCanClose` in `lib/case-tracker.ts` blocks `PATCH /api/cases/[id]/close` until all five are set; `closedAt` is itself immutable once set. Closure also makes the whole case read-only, not just the evidence checklist: `assertNotClosed` in `lib/case-tracker.ts` is called first by every mutation route under `app/api/cases/[id]/**` other than `close/route.ts` itself (advance, draft, approve-draft, evidence, confirm-authority, confirm-jurisdiction, request-confirmation, structured-confirmation), returning 409 once `closedAt` is set — mirrored in the UI by `enforcement-actions.tsx`, `draft-reply-panel.tsx`, and `deadline-chip.tsx`'s `isFinal` state, which swap in a locked/read-only view for a closed case instead of relying on the API rejection alone. Separately, a four-state `status` (`IN_PROGRESS`/`WAITING_ON_CONFIRMATION`/`DEADLINE_APPROACHING`/`COMPLETE`) is a *derived* value, not something any route sets directly: `deriveCaseStatus()` in `lib/case-tracker.ts` is a pure function of the case's current fields, and `lib/case-status-sync.ts`'s `syncCaseStatus`/`syncCasesStatusBatch` call it after every mutation that could change it — and on `GET` routes too, since the deadline-based transition into `DEADLINE_APPROACHING` is time-based and no user action triggers it directly. A transition is persisted and logged (`CaseActionLog` type `STATUS_CHANGED`, note built via `statusChangeNote()` so it interpolates the human-readable `CASE_STATUS_CONFIG[...].label`, never the raw enum) only when the derived value actually changed.

**The draft reply workflow tracks provenance per insertion, not per sentence.** `Case.draftReply` is the editable text; inserting a prior case's reply or a template block (`draft-reply-panel.tsx`) appends text and pushes one `DraftInsertion` (`{id, source: 'PRIOR_CASE'|'TEMPLATE', label, sourceCaseId?, text}`) onto `Case.draftInsertions` (JSON-encoded) — an approximation of "know where each part of the draft came from" scoped to what the UI actually controls (inserts), since there's no real drafting/parsing engine here. `lib/draft-flagging.ts` is a deterministic (not AI) scanner for broad/overstating language and unresolved `[placeholder]` tokens, matching this repo's existing pattern of deterministic mocks over real model calls (see `lib/legal-ai.ts` below). Filing a complaint is an approval-gated action, not just a stage check: `POST /api/cases/[id]/approve-draft` snapshots the current text into `Case.approvedDraftText`, and `assertDraftApprovedForFiling` in `lib/case-tracker.ts` requires that snapshot to still `===` the live `draftReply` — so editing the draft after approval doesn't clear the approval flag, it just stops matching, and re-approval is the expected, repeatable flow (unlike `jurisdictionConfirmedAt`/`authorityConfirmedAt`, this is deliberately *not* immutable). The structured confirmation form (`structured-confirmation-dialog.tsx` → `PATCH /api/cases/[id]/structured-confirmation`) only writes the evidence fields not already confirmed — items confirmed individually beforehand are left untouched — but always logs one `STRUCTURED_CONFIRMATION` entry and clears `confirmationRequestedAt`.

**The dashboard and case tracker are connected by one action plus a durable scalar, not a Prisma relation.** "Track as Case" on a response (`response-detail.tsx` → `dashboard.tsx`) opens the case tracker's `NewCaseDialog` prefilled with that response's broker name/jurisdiction, then on creation navigates to `/case-tracker?open=<id>`. The created `Case` also stores `sourceResponseId` — a plain nullable `String`, not a `@relation` (no FK, no cascade; matches how `applicableRegime` is already stored as a plain string) — so the link survives page reloads: `case-detail.tsx` shows a "View Original Response" link back, and `response-detail.tsx` checks `GET /api/cases?sourceResponseId=<id>` to swap "Track as Case" for "View Case" once one exists, preventing duplicate cases for the same response. This mirrors the pre-existing `/responses?open=<id>` deep-link convention used by Home Overview's Recent Activity feed — all three areas (`/responses`, `/case-tracker`, `/legal-workbook`) read `?open=` via `useSearchParams` (wrapped in `<Suspense>` at the page level, required for that hook) and fetch+select that one record independent of the list fetch.

**All three areas cross-link on jurisdiction, not just Case Tracker.** `lib/jurisdiction-map.ts` exports `matchesJurisdiction(regime, jurisdictionString)` (a loose substring match), used by `RelevantLawPanel` (embedded in both `response-detail.tsx` and `case-detail.tsx`) to show jurisdiction-matched `LawRegime` clauses with an "Insert" action — for a response this inserts into the compose-drawer body, for a case it appends into the Enforcement panel's note field (`enforcement-actions.tsx`'s `insertCitation` prop). `RelevantLawPanel` also has an "Open in Legal Workbook" link per regime (`?open=<regimeId>`), and `legal-workbook.tsx` shows the reverse — a count of cases/responses in the selected regime's jurisdiction, linking back (unfiltered) to those screens.

**Auth is edge-middleware based, not per-route.** `proxy.ts` (Next's middleware, matched via `config.matcher` against everything except static assets) gates every request behind a `br_session` cookie check, redirecting to `/login` on mismatch. Public paths (`/login`, `/api/auth`, `/icon`, `/opengraph-image`) are allowlisted in `PUBLIC_PATHS` inside `proxy.ts` — new unauthenticated routes must be added there.

**Dashboard state lives in one client component.** `components/dashboard.tsx` owns filtering/search/selection/pagination state for the responses view; `sidebar.tsx` (bucket/tag nav), `response-list.tsx`, `response-detail.tsx`, `compose-drawer.tsx`, and `bulk-action-bar.tsx` are largely presentational children driven by it. When adding a new filter or bulk action, it likely belongs in `dashboard.tsx` first.

**Tag taxonomy drives UI behavior, not just display.** The broker-response tags (`CONFIRMED_REMOVAL`, `CONFIRMED_NOT_FOUND`, `NEEDS_MORE_INFO`, `NEEDS_CONFIRMATION`, `FORM_REQUIRED`, `DENIED_JURISDICTION`, `DENIED_FRAUD`, `DENIED_OTHER`, `OUT_OF_OFFICE`, `UNDELIVERABLE`, `SPAM_OR_IRRELEVANT`, `AMBIGUOUS`) are defined once in `lib/constants.ts` alongside status config and email templates, and referenced from `tag-badge.tsx`, `sidebar.tsx`, and `compose-drawer.tsx` (which pre-populates the compose email based on tag). Adding a tag means updating `lib/constants.ts` plus the Prisma `tag: String` field usage — tags aren't a Prisma enum.

**External ingestion is one-way, and this app never runs classification itself — including holding-reply detection and case-worthiness.** `/api/ingest` receives already-classified responses pushed from an external classification pipeline (not built in this repo); `/api/stats` proxies live stats from `email-classifier.purewl.com/stats`. `isHoldingReply` (rendered via `holding-reply-badge.tsx`) and `requiresCaseTracking` + the requester's own location are optional fields the classifier sets on the ingest payload — when `requiresCaseTracking` is true, `/api/ingest` auto-creates a linked `Case` (`sourceResponseId` set) in the same call, deriving jurisdiction from the supplied `userCountry`/`userState` exactly as `POST /api/cases` would. A response's tag can also be corrected after the fact (`override-classification-dialog.tsx` → `PATCH /api/responses/[id]/override-tag`), logged as `ActionLog` type `CLASSIFICATION_OVERRIDDEN` — a human correction surfaced as a signal for the external pipeline, not something this app retrains or auto-applies itself.

**Legal AI content is provider-abstracted.** `lib/legal-ai.ts` defines a `LegalAiProvider` interface (`generateRegime`, `recheckClause`) currently backed by a deterministic mock (`getLegalAiProvider()`), so the feature works with zero API cost. All content generated this way is flagged `aiGenerated`/`verified` in the schema until a human confirms it. A recheck produces a `PendingLawChange` row sitting in front of a `LawClause` — the clause itself never mutates until a change is explicitly accepted or rejected (see `app/api/legal/changes/[id]/route.ts`, `app/api/legal/regimes/[id]/recheck/route.ts`).

**Action logging is append-only.** Every action taken on a response (resolve, escalate, re-send, email sent) is written to `ActionLog` (`prisma/schema.prisma`), keyed by `responseId`, rather than mutating fields on `BrokerResponse` directly — `response-detail.tsx` renders this as history.

**Category config in `lib/constants.ts` is the single source for label + color + explanation.** `BUCKET_CONFIG`, `TAG_CONFIG`, `STATUS_CONFIG` (response status), `STAGE_CONFIG`, `CASE_STATUS_CONFIG` (the four-state case status, distinct from response `STATUS_CONFIG`), and `EVIDENCE_ITEM_CONFIG` each carry a `description` field alongside `label`/`color`/`bgColor`/`barColor` — this is what backs the tooltip on every badge and breakdown row via `components/info-tooltip.tsx` (a thin wrapper around `components/ui/tooltip.tsx`, Radix-based, provider-mounted in `app/layout.tsx`). Adding a new tag/bucket/stage/status/evidence item means adding its `description` here too, not just its color.

**Sidebar nav-rail state persists client-side, same pattern as theme.** `components/nav-rail.tsx` (the primary icon+label nav shared by all feature areas) persists its collapsed/expanded state to `localStorage` under `nav-rail-collapsed`, mirroring the existing `theme-provider.tsx` pattern of reading `localStorage.getItem('theme')` — follow this pattern for any other cross-page UI preference rather than introducing a new state mechanism.

**Interactive elements carry `data-testid` for automation.** Convention: static elements get descriptive kebab-case ids (`nav-home`, `login-submit`); repeated list/card rows get `` `{entity}-row-${id}` `` keyed by the actual record id (not React's internal `key`) so a script can target one specific row. Icon-only buttons also get `aria-label`. Follow this pattern for new interactive UI.
